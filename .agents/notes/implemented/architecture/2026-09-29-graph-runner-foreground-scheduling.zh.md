# Agent Note: Graph 计划在前台运行，节点完成需要证据

Status: implemented

[English](2026-09-29-graph-runner-foreground-scheduling.md) | 中文

## 问题

已准入的 `dsh-graph/v1` 计划必须作为一组独立单元运行，不能信任每个单元对自身的陈述；它必须能在崩溃后继续，并且必须防止并行单元互相覆盖。循环层只约束一个会话；此前没有任何东西调度多个会话、决定一个单元的结果何时算数，或恢复一个部分完成的计划。

## 决策

`@deepseek-ai/dsh-experimental-graph-runner` 注册 `graph_run`。一次调用在调用它的工具调用内部运行某个计划的最新准入版本：在 `maxConcurrent` 范围内进行列表调度，每个代理节点是一个以该节点工具白名单与输出 schema 启动的新一次性子代理，锚点与 verify 命令经过 shell 接缝，人工关口经过调用方代理上的审批。每次状态变化都是调用方会话上的一个 `graph/node` 事件，并由 `graph/run` 的开始与停止事件包围；节点词汇、状态转换表、need 满足条件与节点指纹位于 `@deepseek-ai/dsh-experimental-graph-contract`，使运行器、graph 投影与运行器不变量共用一个定义。

节点只有带证据时才是 `executed`：其 verify 命令以 0 退出（`predicate`），某个验证节点为它返回 verdict `pass`（`verifier`），或某个人批准了它的关口（`human`）。没有证据而完成的子代理会让节点保持 `unverified`；需要它的节点只能跨 `verifies` 边继续。可重试的失败在 `retryBudget` 内以新的简报重新运行，简报从不包含更早的失败。新的准入版本会携带指纹（节点本身及其 needs 的指纹）未变的已执行节点，并把改变的节点标记为 `patched`。一次运行若在日志中发现仍为 `running` 的节点，会以依据 `sessionExited` 把它标记为 `failed_retryable`，并在下一次尝试的简报中要求检查部分变更。节点子代理在节点写入前缀之外的写入与编辑，在 `enforce` 模式下被拒绝，在两种模式下都通过注册在观察策略之前的 `fs/write-intent` 与 `fs/edit-intent` 监听器被记录。

## 考虑过的方案

**把图作为后台作业运行。** 作业在内存中且不可恢复，需要为所有者提供作业控制器，并通过通知消息回报；工具调用返回之后无法再请求审批。前台调用让回合保持打开以供人工关口使用，并使日志成为唯一的恢复状态。

**给每个写入节点各自的 git worktree。** 子会话继承父会话的工作目录，一次性子代理请求没有工作目录字段，因此 worktree 不会改变节点工具写入的位置。取而代之的是在审计时检查写入前缀互不相交，并在写入时执行约束。

**把已完成的子代理算作完成。** 这让一个单元认证自己的工作，而这正是循环层 verifier gate 要防止的失败。完成需要一个谓词、一次独立验证或一个人。

**用目标轮次上限限制重新规划。** 目标轮次统计的是目标驱动的回合，而不是计划版本；`maxPlanVersions` 限制一次运行接受的版本。

## 后果

调用方回合会等待整个运行，而节点的 shell 命令可以写到其前缀之外，因为只检查 fs 接缝。每次运行不执行 token 与成本预算，因为子代理结果不带用量；执行的是墙钟时间与派发次数。verifier gate 等循环层监听器也作用于节点会话内部。作为交换，每个节点结果、重试、携带的结果与停止原因都能从调用方会话的日志重建，运行器不变量在追加时拒绝非法的状态转换、修订号缺口或没有证据的 `executed` 状态。
