# Agent Note: Tool Calls Emulated in the Prompt for a CLI Transport

Status: implemented

## Problem

[Using a vendor CLI as the model transport](2026-09-30-vendor-cli-as-model-transport.md) gave a Claude subscription a model route inside the Harness without any token leaving the CLI. It could not serve a chat turn. Claude Code exposes no way to pass caller-supplied tool definitions and no mode that reports a tool call without executing it, so the route refused any request carrying `GenerateOptions.tools` — and nearly every real turn carries them, including compaction. The picker entry existed and could not answer the first message a user sent it.

Three mechanisms could close that gap, and only one keeps the loop in `agent-loop`: giving the CLI the Harness's tools over MCP moves iteration and the stop decision into Claude Code; lifting the CLI's OAuth grant and calling the vendor API takes on every risk the earlier decision refused; carrying the tool definitions as prompt text keeps the Harness's loop, guards, approvals, and compaction and asks only that the model report a call as text.

## Decision

**A CLI transport carries the request's tool definitions in the system prompt and parses the model's textual call back into a real `tool-call` block.** `@deepseek-ai/dsh-llm-claude-cli` does this under `toolCalls: 'prompt'`, which is the default; `'refuse'` keeps the earlier behavior for a deployment that wants it. The Base Bundle row stays `disabled: true`, so nothing changes for a user who does not opt in.

`src/emulate.ts` owns the mechanism. The preamble is one fixed block of text — the contract for reporting a call, the two bounds the route will enforce, and one entry per declared tool with its `description` and the type of its `arguments` — identified by `PREAMBLE_TEMPLATE` and pinned verbatim by a test. The template is `dsh-tool-call/2`. `/1` listed each `parameters` schema as JSON inside a `json` fence; `/2` renders it as one line per member and falls back to the verbatim JSON Schema for any schema that notation cannot state exactly, which cut the 36-tool preamble of a recorded session from 30,430 to 26,275 characters and from 7,397 to 6,362 billed prompt tokens. `/2` also states as a rule of its own that the block is the only way to call a tool, naming a bare JSON object and XML `<invoke>` tags as things that are not one, and shows the model no fence but the `dsh-tool-call` one: the `/1` preamble the recorded reply had read showed 36 `json` fences beside the one fence the model must write. Whether those fences caused the missing opener is not established. The reply format did not change; the tag changed because the text the model reads did, and a log written under `/1` is reconstructed with the `/1` renderer from this package's history. It is not a tunable: its wording is what makes a reply parseable. The bounds, the retry budget, and lenient reading *are* `Config` fields, because how many calls a reply may carry, how large a call may be, how many correction runs a deployment will pay for, and whether a near-miss call is accepted are deployment choices.

Five consequences were load-bearing enough to design around rather than discover.

**A reply is untrusted text, so every way it can break the contract has one named outcome.** `TOOL_CALL_TRUNCATED`, `TOOL_CALL_MALFORMED`, `TOOL_CALL_UNKNOWN_TOOL`, `TOOL_CALL_TOO_LARGE`, `TOOL_CALL_LIMIT`, and `TOOL_CALL_UNFENCED` each name what the reply did and what a corrected one must do. A call is never dropped in silence, never invented, and never repaired. A rejection is answered by up to `toolCallRetries` correction runs, which resend the request with a notice naming the fault; that replacement is possible only before the first answer text has been handed over, because after that the caller has seen text a second run would contradict, and the rejection becomes the terminal `finish`. Tool calls are not handed over as they close: a reply's calls are held until the reply ends, so a rejection later in the same reply replaces the whole reply and none of its calls run.

**A call written in another syntax is accepted or rejected by name, never answer text.** `agent-loop` ends a turn on a reply that carries no tool call, so a call the scanner does not recognize ends the turn with its raw text shown as the answer. Two recorded `opus` replies did exactly that. One wrote three calls as bare JSON objects, each followed by a closing fence and none preceded by the `dsh-tool-call` opener line. The other wrote Claude's native XML function-call syntax, `<invoke name="…">` elements holding `<parameter name="…">` elements, and ended inside the third. So the scanner holds back any JSON object that opens with `"name"` or `"arguments"`, with a fence opener line directly above it, and any `<invoke>` element outside a fenced code block, with a `<function_calls>` tag directly before it, until the text closes, proves not to name a declared tool, or outgrows `toolCallMaxBytes`. Text that names a declared tool is an attempted call; everything else is released unchanged, including XML inside a fenced code block, where an answer explaining the syntax writes it.

While `toolCallLenient` is on, which is the default, an attempted call is accepted in the three forms where what the model meant is not in doubt: a block opened with `json` or no info string, a bare object followed by a closing fence, each holding exactly `name` and `arguments` with object `arguments`, and a complete `<invoke>` element. The JSON forms are used as written. An XML parameter body is raw text, so it is kept verbatim for a parameter the tool declares as `string` and parsed as JSON for one it declares as a number, integer, boolean, object, or array; an element with a parameter the schema declares no such type for is not accepted, because converting it would take a guess. The recorded replies then yield their calls instead of a correction run that re-bills the whole request. Every other attempted call is rejected: `TOOL_CALL_UNFENCED` when it closed, `TOOL_CALL_TRUNCATED` when the reply ended inside it, `TOOL_CALL_TOO_LARGE` when it outgrew the byte cap. The correction notice states the required block and, for XML, that XML function-call syntax is not accepted on this route. Whitespace that opens a reply is held until other text follows, because the first recorded reply began with a newline, and handing that newline over would have made the rejection terminal instead of correctable.

**The preamble is a new model-visible input, so it is logged.** Each CLI run of an emulated request appends one `llm/cli-tool-emulation` event *before* the run: route, model, template identity, preamble length, declared tool names, the run's number, and the verbatim correction notice a retry carries. The preamble text is not stored, because it is a pure function of the template and the request header's tool schemas, which the log already holds. A request naming a session the store cannot reach fails with `EMULATION_NOT_LOGGABLE` rather than emulating unlogged. Each run whose reply was read also appends one `llm/cli-tool-emulation-reply` event *after* the run: calls accepted, calls accepted leniently, characters discarded after an accepted call, and the rejection code. It is a second event rather than fields on the first because the first must be written before the model reads the preamble, when none of this is known. Both events are new roots and needed no `SESSION_FORMAT_VERSION` change.

**Schema conformance stays with the tool layer.** Structure is checked at this boundary — JSON object, a declared tool name, object `arguments`, the size and count bounds — but `arguments` that break a tool's `parameters` schema are forwarded exactly as written. The Harness's tool layer already validates them and reports a violation to the model as a tool result, which is the same correction path every other provider uses; a second validator here would be a second set of disagreements and would couple a model adapter to the tool runtime.

**Text after an accepted call is discarded, and the loop's system prompt is hoisted.** A model with no way to yield keeps writing after its call and invents the result; the preamble forbids it and the route drops it, recording the dropped length. Separately, a loop-built request leaves `GenerateOptions.system` undefined and carries its prompt as the leading system-role message, so that message is hoisted into `--system-prompt`: without the hoist the Harness prompt would arrive as a labelled paragraph inside the user turn while Claude Code's own prompt stayed in force above it.

## Alternatives considered

**Constrain the reply with the CLI's `--json-schema` structured output.** A schema for `{text, tool_calls[]}` would make the reply valid JSON by construction. Measured and rejected: against Claude Code 2.1.285 the same request went from 1,100 to 9,015 prompt tokens over five internal turns, because the CLI satisfies the schema by running its own tool loop, and the model then reported that no tools were available to it.

**Stop sequences at the closing fence.** They would end generation instead of discarding invented text. The CLI exposes no stop-sequence flag.

**Buffer the whole reply so any rejection can be retried.** It would make a correction run possible in every case, not only before the first chunk. Rejected: an emulated turn is every agent turn, so buffering would remove incremental streaming from chat permanently to protect a path the measured models rarely take.

**A `Config` allowlist of the tools this route declares.** It would let a deployment cut the preamble further. Not added: the measured set is what the session composed, a tool hidden here would still be listed to the user and to every other route, and a call to it would become `TOOL_CALL_UNKNOWN_TOOL`. Composing fewer tools into the session removes them everywhere.

**Accept any JSON object that names a declared tool.** It would turn every near-miss into a call. Rejected: a bare object with no fence is also what an answer quoting an example looks like, and an object with extra members or non-object `arguments` needs a guess about what to keep. Those stay rejections with a correction run.

**Run the complete calls of a reply and drop a call it ended inside.** The recorded XML reply held two complete calls before the truncated one. Rejected: the loop would run two calls and the model would never learn its third was lost. The whole reply is rejected by name, and because a reply's calls are held until it ends, none of them has run when the correction run replaces it. The cost is that a call card appears when the reply ends rather than when each call closes.

**Detect an unfenced call only after the reply ends.** Scanning the finished text would need no held-back object. Rejected: by then the JSON has been streamed to the user, and a correction run can no longer replace the reply.

**Terminate the child as soon as the last call closes.** It would stop paying for the invented continuation. Rejected: the CLI reports usage and the stop reason only in its terminal `result` message, so this would trade exact token accounting for a few output tokens.

**Validate `arguments` against the tool schema here and retry.** Rejected above: it duplicates the repository's one JSON-Schema validator and would make a model adapter depend on the tool runtime and its peers.

## Consequences

A Claude subscription can serve the main chat model. The Harness keeps its loop, its guards, its approvals, and its compaction, and a tool-bearing turn completes: against the installed CLI, `sonnet` reads `/etc/hosts` through a real `read_file` call and then answers from the tool result it is handed.

It costs prompt tokens and it depends on the model's obedience. Measured with `haiku`, the fixed contract text is 385 billed prompt tokens and five small tool declarations are about 42 each; only the contract block is overhead a provider accepting a `tools` field would not charge for. A real session declares far more: 36 tools cost 6,362 tokens, and half of those characters are the tools' own `description` strings. Nothing constrains the reply, so a weak model is a real failure mode: `haiku` sometimes wraps a correct block in stray `<function-calls>` tags, which parse but survive as assistant text, while `sonnet` was clean on every attempt. The route is worth enabling with a strong model and not with a weak one.

Streaming pauses at a fence: text is released as soon as it cannot open one, so a plain answer streams, but a reply that opens a fence shows nothing more until the block closes. It also pauses at a JSON object that opens with `"name"` or `"arguments"`, until that name is complete and undeclared or the object closes. It pauses the same way at an `<invoke>` tag. An answer cannot show a call to a declared tool as an example, as a JSON object anywhere or as XML outside a fenced code block: it is read as an attempted call. A correction run repeats the whole request, and the abandoned run's token usage is not reported because its child is terminated the moment the reply is rejected — the session log records that the run happened.

Nothing changes for a user who does not opt in: the row still ships disabled, and enabling it is one id-targeted override.
